## 2. 结论：**不是新缺陷，是 R34 已经登记过的那格盲区**，而它今天仍然成立

`UICaptureHarness.swift:4783-4816` 那条资格判据（`menuSurfaceReplicaFixtures`）断言的正是
"第一行最右墨 ≥ 帧宽"，并打出：

```
MENUBAR_REPLICA menubar-recommendations 第一行最右墨=… / 帧宽 320
⇒ 复刻顶到帧边界，产品是 NSMenu（.menu 风格）⇒ 这批帧不判宽度/截断/对齐
```

⇒ 我看到的现象 = 这条声明的**预期形状**：`MenuBarExtra` 默认 `.menu` 风格 ⇒ 内容被编译成真 NSMenu，
离屏 `cacheDisplay` 画的是复刻而不是那个表面，所以这六帧对宽度/截断/对齐**没有发言权**。
本轮的独立复现（左边距 0–3、右边距 0–2，6/6 帧）说明：**声明还没被"顺手修好"冲掉**，
资格判据仍然有必要。若哪天有人给行加了右边距，那条断言会红并要求重判 —— 形状是对的。

真机那一腿也不是没账：R2-22（菜单真弹出来的样子只能人眼核对）与 BACKLOG 里
"④ 菜单栏的原生 `NSMenu`" 那条捕获通道边界已经把它记着 ⇒ **本轮不开新单**（R88 的教训：开单前先查）。

## 3. 本轮真正抓到的一条：我自己这颗临时尺只能答"这行有没有东西"，答不了"文字内边距"

`r89_menubar_review.py` 把 `Divider()` 那几条横贯全宽的行读成了"文字带 x=0…639、对比 5.47:1"，
还给出"峰值墨=221"这种听着像结论的数。⇒ 补了一条**正对照**（同一颗尺读一张已知有内边距的帧）：

```
settings-data-720x540-dark  真文字带：左边距 = 35 / 78 / 296（@2x ⇒ 17.5 / 39 / 148pt）
                            全宽图形行：左边距 = 0、右边距 = 0、"对比 5.47:1"
```

⇒ 尺的**能**与**不能**就此划清：真文字永远不会报 0（正对照证明了这一点），
所以菜单栏那六帧报 0 不是"尺坏了"；但它报的 0 也**不区分**"文字贴边"与"那是一根横贯全宽的分隔线"——
`UICaptureHarness.swift:4799-4800` 早就写过同一件事（"整段框进来会读到两条横贯全宽的 `Divider()`"）。
⇒ 采信范围：本轮只采信"左边距/右边距 = 0"这一条**与眼睛一致、且与 R34 的登记读数同向**的读数；
对比度、带高、峰值墨这些一律不入库、不写进台账结论。要把这颗尺升成判据，得先让它会分"文字 vs 分隔线"
（现成的路子是只框第一行那 16pt 带，像 R34 那样，而不是整段扫）。
