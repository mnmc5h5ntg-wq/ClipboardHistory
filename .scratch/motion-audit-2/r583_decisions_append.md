## D-583（R583 · 2026-11-06 · 第 582 轮 / Round 580）：门的退出码要按**态**数，不按步骤绿数；登记必须是可数的账（含它自己会腐烂的三种形状）；"占位文字"与"读数"的差别是前缀不是空不空

① **"这一步绿了"与"这一态被判过"是两个量，而只有后者是我想要的那个。** `frame_baseline.py check` 的 `return 1 if missing else 0` 不是 bug —— 注释写着"多帧与变帧交给人判断"，那是**有意**的设计；代价是它把"人判断"这件事默认给了一个每轮只有 3 分钟预算的会话，于是本机那 8 张变帧从 R577 起连续四轮逐字相同地挂在 `CHANGED=8` 上，CI 那一步一直绿。⇒ 规矩：**引用一次门的结果，要同时引用它判的是哪一列**（R582 ⑨ 里已经记过同形的一条：`frame_baseline.py check` 的退出码只判 missing ⇒ 门绿不许读成"八张已签收"）；而**"交给人判断"这一态在本仓库里必须落成账**（逐张登记），否则它就是"没人判"的委婉说法。

② **登记要可数，就必须连"名册自己会腐烂"一起判。** 本轮的门不是"加一个豁免名单"，而是四条判定：⑴ 变帧/新帧每张都要有一行（`kind` 对得上）；⑵ 行的 `reason` 与 `ticket` 不许为空；⑶ 行的帧名必须对得上基线（拼错的、夹具改名后留下的 ⇒ 红）；⑷ 名册读不出来 ⇒ **退 2**，不许降级成"0 条登记"再判绿或判红（R99 那一族：解析器坏了会安静地给 0 条然后全绿）。⚠ 同时必须**明写哪一态故意不判**：**陈旧行**（这台机器此刻不漂）只报数 —— 漂移是按机器的，把它判红等于逼人在两台机器之间来回删行；而这条"不判"不能只写在注释里，要写成**断言它不红**的电池格（R579 那一课：名册形状要靠被引用才红 —— 这里靠电池格才不会被"顺手改成红"）。

③ **"占位文字"和"读数"的区别是前缀，不是空不空。** 本轮我自己踩的：`ci_status_r583.py` 未到数时那一格写的是"未取（那一跑未到数）"，这是**非空字符串**，而我第一版分支写 `elif registry:` ⇒ 三条待验形状被判成"读到了但不匹配"的新形状（也就是"门在响但没人听得懂"）。⇒ 规矩：**分支先问"那一行到底在不在"（按通道串前缀判，如 `startswith('D12_SHAPE_SCAN_REGISTRY')`），再问它说什么**；占位文字必须与读数**形状上不可混淆**（前缀、大小写、是否含通道串名），否则任何 `if 值:` 都会把"没有"读成"有"。这一条与派单 ① 那句"三者修法相反，不许并成一句"是同一处：判错分支就会按错的处置办。

④ **ASCII 双引号包 CJK 那一族不属于"python 源码"，属于"任何被解析成字符串的字面"。** 本轮同一族炸了两次：一次在 python 源码（`print(... 不许当"没有登记" ...)` ⇒ `py_compile` SyntaxError），一次在 **JSON 值**里（登记名册 ⇒ `json.load` 失败）。⇒ 规矩的形状要推广：**Swift 字面量、JSON、YAML、shell、python 都算**；写这类文本时统一用「」，并且**每次写完立刻用解析器自证**（`py_compile` / `json.load` / `swift build`），别等下游脚本撞上来。这一族从 R579 起记到第 **十一** 次，且本轮两处都在写盘之前被抓到 —— 抓到得早不等于没犯。

⑤ **推翻一条旧断言时，它的夹具要一起重做，不许反过来把判定改回去。** 新语义下 `test_allow_missing_only_absolves_the_named_frames` 立刻红：那份测试用**假哈希**（`{"a.png": "1"}`）写基线，于是新门"看到"两张变帧 —— 红的是我的夹具，不是产品，也不是新门判错。另一格 `setup()` 把 changed 与 missing 混在同一份合成数据里，于是"只测一态"的断言其实测了两态。⇒ 规矩：**合成数据必须只偏离被判的那一维**（其余维用真值/真哈希），否则一次改动会同时动两维，红的到底是哪一维就说不清（R577 那条"一臂里捆两件产品各自会做的事就永远判不出必需是哪一件"的又一形状）。同族对照：本轮把旧断言"加帧不该红"**显式推翻并写明理由**，而不是把 added 那一半的判定偷偷删掉 —— 推翻契约要在账上留名字，改判定去迁就旧断言就是假绿。

⑥ **成因问题先问"是哪一段代码在改它"，再问"要不要统一"。** 派单 ③ 给的事实是"shell 与 python 都打原样大小写，Swift 那份是小写"，直觉结论是"python 侧改了大小写"。本轮没有接受这个直觉，而是在**同一次会话**里取四通道逐字读数，并额外从 Swift 里直接调 raw `gethostname()`：raw=`MacBook-Air.local`、`ProcessInfo.hostName`=`macbook-air.local`、`lowercased(raw)` 与后者**逐字相等** ⇒ 改大小写的是 **Foundation**，python 与 shell 都没动。⇒ 规矩：**"两份实现取值不同"要先量到"哪一段代码做的变换"**（能直接调底层原语就调一次原语），否则统一方案会往错的那一侧改；而"要不要统一"是**口径选择**，归用户（往 python 那侧统一会改写已登记好的红名单的键 ⇒ 354 那一族全线失效）。
