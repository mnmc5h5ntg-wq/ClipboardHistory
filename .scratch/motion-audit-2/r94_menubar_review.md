## 2. 动效 / hover 的逐条判断（阶段二要求"每个位点都要判"）

* **菜单项 hover**：不加自绘高亮。证据：六张帧里**没有一块背景底**——所有带的字身高都是
  12.5 / 13.0 / 10.5pt 的纯文字带，若 SwiftUI 侧留了一层按钮底，带高会被圆角底拉大（R20 那颗尺）。
  高亮由 `NSMenu` 自己画（账本 U-1 / D-055），这条通道量不到它 ⇒ 维持现状，理由成立。
* **按压态**：不接。同 hover：菜单高亮已经是"收到了"的证据，再叠一层会把 U-1 拆掉的卡片感装回来。
* **空 ↔ 有推荐之间**：不加淡入。`MenuBarExtra` 默认 `.menu` 风格 ⇒ 内容编译成真 `NSMenu`，
  SwiftUI 的 `.transition` 在那一层根本不执行（R5 / D-055 实测）⇒ 留声明就是留假账，现状是对的。
* **加载态**：不画转圈（代码注释已写：不动的图标 + 一句"正在整理"比一个假转的指示器诚实，也不会让人以为点了能取消）。
* **标题 / 小标题**：唯一可能值得动的是**对齐**（居中 → 与行共用左轴），但它落在 R34 登记的表面盲区里，
  而 macOS 12 那条路径用的是原生 `NSMenuItem(title: "时间剪史")`（AppKit 自己左对齐）
  ⇒ 两条路径**可能**不一致，但这条通道没资格判 ⇒ 开 **136** 真机核对，不在本轮改产品。

## 4. 本轮抓到三条**尺**的错（都进台账，都不算产品缺陷）

* **U-218**：`r86_heatmap_legend.decode()` 返回的是 `(w, h, ch, rows)`，而 `r92_data_visual.lum()` 返回
  **WCAG 的 Y ∈ [0,1]**（实测 `lum((39,39,39)) = 0.0203`）。把 Y 直接跟 12、25 这种 255 尺度的阈值比，
  结果是六张帧全部"带数 = 0"——**"量不到"被伪装成"没有"**（R90 那一族的反向版本）。
* **U-219**：墨的判据从"ΔL 门槛"换成"对比度比值门槛"。同一根原生 `Divider()` 两个主题都是 ≈1.25:1，
  可 ΔL 是 亮档 53.2 / 暗档 5.4 —— WCAG 的 Y 在高端近乎线性、低端被压扁，
  于是**一个固定 ΔL 门槛在两档上灵敏度不同**（第一次跑就是亮报 3 条线、暗报 0 条，而那 0 是门槛不是画面）。
* **U-220**：两档"同形"的判据不许用逐点相等。实测差 0.5pt（74.0 vs 73.5、144.0 vs 143.5、174.5 vs 174.0）
  是抗锯齿落在哪一行；用相等会三帧全报"不同形"⇒ 一把只报假的尺比一把没做的尺更贵（R83 贴边假峰同族）。
  现在：容差 1.0pt，并把最大偏差本身打出来（容差要能量出来，不是拍脑袋）。
