# 时间剪史 v1.4.7

v1.4.6 之后的小修正版。v1.4.6 的产物构建于 tag 指向的 `e4ac62b`，而下面这项修复是在那之后才合入 main 的，
所以单独出一版，v1.4.6 保持不动。

## 修复（唯一一项产品行为变化）

- **卷根目录下的文件，父目录标签不再显示成 `…/..`**。详情区与多文件列表里，文件记录显示「…/上一级目录名」
  而不是完整绝对路径；当文件直接位于卷根（例如 `/报告.pdf`）时，旧实现在部分 Foundation 版本上会把父路径
  算成 `/..`，标签于是变成 `…/..`。现在先标准化再取目录名，根目录一律显示 `…`。
  - 触发条件如实说明：这条只在 Foundation 给出 `/..` 的那类系统上显形（CI 的 macOS 15 / Swift 6.1.2 就是），
    macOS 26/27 上原本就显示正确 —— 所以装了 v1.4.6 的机器看不出差别，本版是补严谨而非救急。

## 构建与测试可靠性（不改变产物行为，但决定能不能编出来）

- 测试不再覆写 XCTest 的 `tearDown()`：原来的 `try await super.tearDown()` 在 GitHub runner 的 Swift 6.1.2
  下被判并发错误，导致**测试 target 在 CI 上根本编译不过**（本机 6.2.1 却通过）。改为每条用例开头复位偏好
  设置，用例顺序从此无关。
- 发布脚本显式把子进程的 `SDKROOT` 对齐到 `xcrun` 的解析结果：`/usr/bin/python3` 会给整棵子进程树注入
  CommandLineTools 的 SDK，而编译器来自 Xcode ⇒ 脚本里的 `swift test` / `make dmg` 必然失败。
- 发布流程文档补上第 5 步（提交 / tag / 推送 / 上传）与两条实测坑，其中一条是
  **Release 附件名不要用中文**：GitHub 会吞掉非 ASCII 前缀，导致 `.sha256` 里记录的名字与实际附件名不一致，
  用户下载两个附件后 `shasum -c` 必然失败。本版附件一开始就用 ASCII 名。

## 验证结果

- 单元测试：`swift test` 229 例（1 例按设计 skip）、0 失败；清空 `.build` 后干净重建 0 编译告警。
- 发布脚本测试：18 例通过。
- CI：main 上 7 步全绿（含「构建零告警」与「执行用例数只准涨不准跌」两道闸）。
- 打包：`make dmg` 退出码 0，`.sha256` 自校验通过。
- 父目录标签新增/加强的断言：`/a.txt → …`、`/Applications/X.app → …/Applications`、
  `/Users/someone/Documents/项目/a.swift → …/项目`。

## 校验

下载本页的两个附件后，在同一个目录里执行：

```
shasum -a 256 -c ClipboardHistory_v1.4.7.dmg.sha256
```

预期输出 `ClipboardHistory_v1.4.7.dmg: OK`。

## 兼容性与升级

- 最低系统 macOS 12 Monterey；Intel + Apple Silicon 通用二进制。
- **数据格式不变**（`history.json` 仍是 v1），从 v1.4.6 或 v1.3 覆盖安装都不影响已有历史；旧版本也能读回本版写的存档，降级可运行。
- 本版仍是本地 ad-hoc 签名、未经 Apple 公证，首次打开可能需要手动允许（见 README 的「如果提示 Apple 无法验证」）。

## 与 v1.4.6 的关系

两版功能一致。除上面那条父目录标签修复与构建/测试可靠性改动外，没有其它产品行为差异；
v1.4.6 的发布说明仍然有效，这里不重复。
